# Project Brief: [Working Title] — Privacy-First Trail App

## Vision
An open-source, privacy-respecting alternative to AllTrails: a native mobile app for discovering and navigating hiking trails, built on OpenStreetMap data, with optional community features that never compromise user privacy or lock users into an account.

## Core Principles (non-negotiable)
- **No account required** to browse trails, view maps, download offline data, or save favorites locally.
- **Local-first storage**: favorites, downloaded maps, and personal data live on-device by default. No cloud sync unless the user explicitly opts in for a specific reason (e.g., sharing a review).
- **Community features are opt-out by default** — off until the user turns them on.
- **No data collection or sale.** No analytics SDKs, no ad trackers, no third-party OAuth login by default.
- **Security by design, always encrypted.** All network traffic uses TLS 1.2+/1.3 only — no plaintext HTTP, ever, for any request this app makes now or in a later phase. Personal/sensitive on-device data (favorites, any future GPS traces pending submission, auth tokens) is encrypted at rest; bundled public map/trail/terrain data is not, since it's identical public OSM data on every install and carries no privacy value to protect. Built to FIPS/STIG-grade rigor — strong ciphers, no deprecated crypto — as a design bar, not as formal FIPS 140-2/3 module certification or a STIG audit, which are ongoing compliance programs scoped to regulated/government deployments this project has no actual need to pursue. See `docs/DATA_ARCHITECTURE.md`'s "Security & encryption baseline" section.
- **Funded by donations** and other non-binding funding — no VC pressure to monetize user data later.
- **Fully open source.**

## Tech Stack
- **Framework:** React Native + Expo (chosen for beginner-friendly tooling, large ecosystem, cross-platform from one codebase)
- **Map rendering:** MapLibre Native (open-source, no dependency on Google/Apple/Mapbox proprietary services)
- **Map data:** OpenStreetMap (via Overpass API for trail data), rendered via vector tiles
- **Vector tile source (to start):** hosted provider (Protomaps or MapTiler) — self-hosting tile generation (OpenMapTiles/Planetiler) is a possible later migration, not a Phase 0/1 requirement
- **Additional trail data (later phase):** US gov sources — USGS, National Park Service, USFS — merged with OSM data
- **Local storage:** on-device (e.g., expo-sqlite) for favorites and offline map/trail data
- **Platforms:** iOS first priority, Android second — both via the same React Native codebase
- **Dev environment:** macOS (M4 Pro MacBook Pro), Xcode for iOS, Android Studio for Android emulator/testing

## Explicitly Rejected Approaches (don't suggest these)
- Forking CoMaps or another existing native (C++) map app — decided against due to language/learning-curve mismatch and because the community/review layer (the actual novel part of this project) isn't something an existing nav app codebase helps with.
- Proprietary map SDKs (Google Maps SDK, Apple MapKit as primary renderer, Mapbox's current closed offering).
- Third-party OAuth (Google/Facebook login) as a default or required sign-in method.
- Building native Swift/Kotlin as two separate codebases instead of one cross-platform codebase.

## Phased Roadmap
**Phase 0 — Environment & fundamentals**
Get Node.js, Expo CLI, Xcode, and Android Studio set up. Blank Expo app running in iOS simulator and Android emulator.

**Phase 1 — Map proof of concept**
MapLibre Native rendering inside the app, connected to a vector tile source. Pull hiking trail data from OSM via Overpass API and render it on the map.

**Phase 2 — Trail browsing**
Trail detail view (name, distance, elevation gain, difficulty from OSM tags). Search/filter by location and attributes. No accounts, no local storage yet. **Target interaction model (built 2026-07-20):** trailheads, not individual trails, are what's visible on the map by default — showing every trail as a highlighted line clutters the screen and overwhelms users. The basemap's own thin/dotted path rendering stays visible underneath (context, not clutter). Tapping a trailhead reveals the trail(s) starting there; if there are several, the user picks from a list, and the map highlights just the chosen trail. See `docs/DATA_ARCHITECTURE.md`'s "Trailhead-based browsing" section for how trailheads get identified and how it works as built.

**Park info panel (planned, one open question left before this is scoped):** tapping a park's boundary/tag should expand `src/components/park-info-panel.tsx` beyond just the name — a Wikipedia summary and photos (publicly available ones to start, user-submitted ones later, AllTrails-style, tied to the Phase 5 account system). **Resolved 2026-07-20:** a live Wikipedia fetch is an accepted, disclosed exception to the zero-network-call bundled-region architecture — OrganicMaps, CoMaps, and Apple Maps all do the same thing, and pretending this app has zero third-party exposure everywhere would be the actual dishonesty, not disclosing a reasonable one. See `docs/DATA_ARCHITECTURE.md`'s new data inventory row. Still not speced: where public photos actually come from (Wikipedia Commons? a specific licensed source?) — needs its own clarifying pass before it's real roadmap.

**Phase 3 — Local-first & offline**
On-device storage for favorites [done]. Full downloadable offline regions: the user picks an area — by searching a name, drawing a box, or tracing a route corridor (see `docs/DATA_ARCHITECTURE.md`'s "Offline region selection modes") — and downloads everything needed for genuine no-signal trail use: trails, points of interest, and topography (elevation/contour shading), not just a bare basemap. **Note:** a same-day proof of concept shipped ahead of this (see Current Status below) that bundles one single hardcoded region with a reduced feature set (no POI, no topography, no region-picker UI) — that's a mechanism demo, not this feature. This line is the actual target.

**Phase 4 — Government data integration**
Merge USGS/NPS/USFS trail data with OSM data. Note: schema reconciliation across agencies is a data problem, not just an API integration.

**Phase 5 — Accounts, reviews, opt-in community**
Minimal backend: auth, database for reviews, moderation tooling. Privacy-respecting auth (avoid default third-party OAuth). Community features off until explicitly opted into. **Also includes community trail contribution:** users can submit missing trails/trailheads this app's initial build missed — nobody knows a trail better than the people who actually hike it — via GPX import or live GPS tracing (GPS tracing is fully optional, never required to contribute), and group existing fragmented OSM way segments into one named route (an OSM route relation) rather than moving/editing any existing geometry. Contributions feed back into real OpenStreetMap, not a separate app-only database, so the whole OSM ecosystem benefits, not just this app. Requires the same lightweight pseudonymous account as reviews (needed for attribution/moderation) even though browsing/favoriting stays fully accountless. Raw geometry editing of existing ways (moving/reshaping a way someone else already drew) is explicitly out of scope for this phase — it needs real conflict-resolution/versioning that new-trail submission and route-relation grouping don't, and is a later increment. See `docs/DATA_ARCHITECTURE.md`'s "Community trail contributions" section.

**Phase 6 — Launch prep**
Privacy policy matching actual code behavior, app store privacy disclosures, donation/funding page.

Nothing in this entry is built yet — documentation only.** Two new decisions worked through with the user before touching code, both now reflected in Phase 2/5 above and in `docs/DATA_ARCHITECTURE.md`'s new "Trailhead-based browsing," "Community trail contributions," and "Security & encryption baseline" sections:
  1. **Trailhead-based browsing** (Phase 2 target): trailheads become the default visible thing on the map, not every trail line — clicking a trailhead reveals the trail(s) starting there (a picker list when there's more than one), and only the selected trail gets the bold highlight; unselected trails stay visible only as the basemap's own thin/dotted path rendering underneath, not hidden and not bold. Built to FIPS/STIG-grade rigor as a design bar (strong ciphers, no deprecated crypto), explicitly **not** pursuing formal FIPS 140-2/3 certification or a STIG audit — those are ongoing compliance programs for regulated/government deployments, not a fit this project actually needs; the user confirmed this reading directly rather than the heavier interpretation.

- **Contour lines shipped, closing out topography for all 3 regions.** Same bundled `terrain.pmtiles` as hillshade and elevation gain, but contour tracing needs a full 2D elevation grid rather than point samples — new script `src/data/scripts/generate_contours.py` mosaics every z11 tile covering a region's bbox into one raster via GDAL (installed via `brew install gdal`; Pillow/numpy layered into the same Python environment via a `--system-site-packages` venv, since Homebrew's Python blocks global pip installs). Correctness detail that mattered: built the mosaic and traced contours in Web Mercator (EPSG:3857), reprojecting to lon/lat only at the very end — XYZ tiles are only pixel-uniform in that projection, so building the mosaic directly in lon/lat would have silently warped every line. Verified against real data before trusting it: Guadalupe's traced elevation range (3,675-8,661 ft) matches the park's real range closely. Picked a 60m interval after actually measuring the tradeoff, not guessing: unsimplified output was 4.3-10.6MB per region; adding a 30m simplification pass (matching the DEM's own resolution) cut that by ~95% with no visible quality loss, landing at 196KB-2.3MB per region depending on area size and relief (Big Bend largest, both because it's the biggest bbox and the most vertical relief). One real bug caught by on-device testing, not assumed: MapLibre logged "Invalid geometry in line layer" the first time this rendered — traced to 147 zero-length segments (consecutive duplicate points) left over from simplification; fixed by deduping consecutive points before writing the final GeoJSON, confirmed the warning is gone on reload.
