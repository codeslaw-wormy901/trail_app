# Data Architecture

This document is the source of truth for "what data exists in this app, and where does it live." It exists so that every future feature gets checked against it before it's built, and so [PRIVACY_POLICY.md](PRIVACY_POLICY.md) is always a description of the architecture, not a wishlist. When these two documents disagree, this one wins, and the policy needs to be fixed.

**Rule for using this doc:** before adding any new field, table, API call, or third-party service, add a row here first. If you can't cleanly describe where the data lives and who can see it, don't ship the feature yet.

## Legend

- **Status**: `live` (exists in the current build), `planned` (Phase 3+ per [PROJECT_BRIEF.md](PROJECT_BRIEF.md), not built)
- **Leaves device?**: whether the data (or a derivative of it, like a query containing it) ever crosses the network
- **Default**: on/off out of the box

## Security & encryption baseline

A cross-cutting principle, not tied to one data type — applies to everything above and everything built later.

- **In transit: TLS 1.2+/1.3 only, no exceptions.** Every network request this app ever makes — Overpass/MapTiler fallback fetches for unbundled regions, future R2-hosted region downloads, the Phase 5 backend, OSM contribution submissions — uses TLS 1.2 or 1.3. No plaintext HTTP, ever, for any request, including ones that seem "low stakes" (e.g., fetching a public map tile still reveals the requester's IP and browsing pattern to whoever's on the network path).
- **At rest: personal/sensitive data only, not everything.** Encrypted: favorites (`expo-sqlite`), any future GPS trace pending submission, any future auth token. **Not** encrypted: bundled public map/trail/terrain data (`src/data/regions/`) — it's identical public OSM/Protomaps/Mapterhorn data on every install, carries no privacy value, and encrypting it would add real complexity and performance cost for nothing gained. This is a deliberate scoping decision, not an oversight — "encrypt everything uniformly" sounds simpler but actually obscures which data the encryption is protecting *for*.
- **Design rigor, not formal certification.** Built to FIPS/STIG-grade practices — strong, current ciphers; no deprecated/weak crypto (no MD5, no SHA-1 for anything security-relevant, no unencrypted transport); OS-native secure storage APIs (Keychain on iOS, Keystore-backed encryption on Android) for anything encrypted at rest, rather than a custom crypto implementation. This is explicitly **not** a commitment to formal FIPS 140-2/3 module validation or a STIG compliance audit — those are ongoing, resource-intensive compliance programs built for regulated/government deployments, and this project has no actual need to carry that overhead. If a real reason to pursue formal certification ever shows up, that's a new decision to make deliberately then, not something to back into now.

## The tile host problem (resolved for all currently-bundled regions — read this for why it matters elsewhere)

Every map app that isn't fully self-hosted has this issue, and it's worth being honest about instead of glossing over: to render a map tile, *something* has to receive a network request for "give me the imagery for this lat/lon box," and that request necessarily includes the requester's IP address. This is true even for MapLibre (open-source renderer) because the renderer still needs tiles from somewhere.

**Update: this is now fully resolved for the 3 regions this app currently bundles (Guadalupe Mountains NP, Big Bend NP, Sam Houston NF).** Each region's basemap is a bundled PMTiles archive extracted once from Protomaps' open, public build (via `pmtiles extract` against a bounding box — see `src/data/README.md`) and read locally through MapLibre's native `pmtiles://` support. There is no tile host for any of these regions at all anymore, not even a well-behaved one — zero requests, to anyone, ever, for map imagery. This happened faster than planned: it was originally scoped as a Phase 3+ migration (see the history below), but once trail data got the same bundled treatment for the same reason, extending it to tiles was a natural, quick next step, not a big separate undertaking.

This section's original reasoning is kept below because **it still applies the moment this app needs a region outside the bundled set** — MapTiler (or a similar live host) will be needed again for any area that isn't worth bundling, and the reasoning for how to choose and limit exposure to that host doesn't go away:

1. **No compounding identifier.** Never attach a persistent client ID, account, or auth token to tile/Overpass requests. Each request is only as identifying as a bare IP address — nothing lets the tile host link today's requests to yesterday's.
2. **Cache aggressively.** Once an area is fetched live, don't re-request it.
3. **Tile host, decided for live fetching: MapTiler.** Compared against Protomaps' hosted API — MapTiler publishes a specific, concrete commitment for the actual tile-serving path (Cloudflare-fronted, IPs held a maximum of 20 minutes then destroyed, no personal data handled by MapTiler itself for tile requests) and has a consumer-friendly free tier (100k requests/month, then maps simply stop loading — no surprise bill). Protomaps' hosted API has a higher free ceiling (1M requests/month) and a strong general privacy philosophy, but no equivalent *published* log-retention specifics for that endpoint could be found. Also confirmed: raw `tile.openstreetmap.org` is not an option at all — its own usage policy explicitly bars production apps and specifically prohibits "download for offline use" style features, which is exactly why an intermediary exists.
4. **Self-hosting/bundling tiles (via Protomaps' open PMTiles builds) is the real long-term fix** — already done for this app's 3 bundled regions (above). The remaining work, whenever it's needed, is deciding per-new-region whether to bundle it the same way or fall back to live MapTiler for areas not worth bundling.

The privacy policy needs to say this plainly rather than imply the app has zero third-party exposure everywhere, forever — it might not, once regions outside the bundled set exist — and pretending otherwise is the kind of gap that erodes trust worse than disclosing it would.

## Overpass: from live fetch to bundled static data (done, not just planned)

Live testing hit real, sustained Overpass unavailability (both public mirrors unreachable — not just rate-limited, the status endpoint itself was unreachable too). Investigation found Overpass's operators have been blocking large Azure/AWS IP ranges over abuse from other tenants on that infrastructure, plus broader recent availability complaints from unrelated apps — this wasn't only about our own traffic. It's a live example of exactly the constraint already noted elsewhere in this doc: depending on the shared public instance indefinitely is fragile.

This was originally written up as an *eventual* direction, not urgent — but it turned out to be straightforward enough to just do immediately, rather than wait: **no live Overpass query engine, ever, for this app.** Instead, a regional OSM extract (Geofabrik's free Texas extract, cropped with `osmium-tool` down to each region's area) was pulled once and pre-processed into the exact static JSON shape the app expects — see `src/data/README.md` for the exact reproducible steps, now generalized into `src/data/scripts/build_catalog.py` and `transform_region.py` rather than one-off hand-run commands per region. This is genuinely cheaper and simpler than any live-query alternative (no server to run at all for this data), and it's the same funding story already worked out in [FUNDING.md](FUNDING.md) if and when it's needed for other costs — not a separate cost problem.

Two concrete things this surfaced, worth remembering:
- **osmium assembles multipolygon relations correctly on its own** — the hand-written ring-stitching algorithm in `use-park-boundary.ts`'s git history turned out not to be needed for this bundled path. Still worth keeping in mind if live Overpass fetching (which returns raw unassembled way segments, not pre-assembled areas) is ever reintroduced for an unbundled location.
- **OSM tagging for "national park" is inconsistent even within one state** — some parks (Guadalupe Mountains, Big Bend) use `boundary=protected_area` + `protection_title=National Park`; others (Amistad, Waco Mammoth) use `boundary=national_park` directly. `build_catalog.py`'s categorization logic now handles both forms rather than assuming one boundary tag covers every national park.

## Multi-region catalog (proof of concept — 3 of ~50+ curated Texas candidates, not yet the full Phase 3 feature)

A Regions screen (`src/app/regions.tsx`) lets the user switch between bundled regions; the Explore map (`src/components/trail-map.tsx`) re-renders its trails, boundary, basemap, and camera position to match whichever region is selected (in-memory only, via `useSelectedRegion()` — not persisted across app restarts). Currently 3 regions are bundled this way: Guadalupe Mountains NP, Big Bend NP, and Sam Houston NF, chosen out of a curated 50-entry Texas catalog (`src/data/scripts/texas-catalog.json`) that `build_catalog.py` can already produce from a full-state OSM extract.

**Explicit callout so this doesn't get confused with the real thing:** this is a proof of concept for the underlying *mechanism* — regions are still hardcoded into the app binary at build time (`REGION_ASSETS` in `src/data/regions.ts` needs a manual code change per new region), and each region's content is still reduced (POI names + icons, hillshade + per-trail elevation gain + contour lines, but no general map text — place names, road names — at all). It proved bundling + a working picker UI end to end with zero network calls; it is not an instance of the real Phase 3 feature described below. Getting from "3 hardcoded regions" to "user-searchable, user-downloadable regions across the whole US" needs: real external hosting (Cloudflare R2 is the current plan — see the size estimates and hosting discussion this catalog work triggered), and a runtime fetch replacing the static `require()` registry.

## Offline region selection modes

Downloading a region for offline use (Phase 3) needs to support three different ways of picking "what area" — modeled loosely on how OrganicMaps/CoMaps handle this, plus a more personalized option those apps don't offer. Whichever mode picks the area, **what gets downloaded needs to be the full experience, not just a bare basemap**: trails, points of interest, and topography (elevation/contour shading), matching what a user would expect from "download this area for offline use," not a stripped-down preview of it.

**This is still ahead of where the multi-region catalog above currently is** — that proof of concept demonstrates mode 1's underlying mechanism (bundle a named region, zero network calls) but not the real feature: it needs a UI for all three modes below, and real hosting so regions are downloaded on demand rather than bundled into the app binary at build time — POI (icons + names) and topography (hillshade, per-trail elevation gain, and contour lines) are now fully in place for all 3 bundled regions.

1. **Search a predefined region (city/town/park boundary).** The simplest case: the world is pre-sliced into named regions ahead of time (state, metro, or park-sized chunks), each hosted as a static file. Picking one is just "download this named file" — no per-user computation happens, and the privacy exposure is minimal: a request for a named public file, nothing that reveals a personal pattern.

2. **Draw or zoom to a box.** The user picks an arbitrary rectangular area on the map. This slices a region out of the tile archive on demand (e.g. via `pmtiles extract --bbox=...` against a larger archive). Privacy exposure here is about the same as ordinary map browsing — a bounding box is roughly as revealing as the viewport you're already looking at.

3. **Route + buffer corridor** (e.g. a planned Austin→Anchorage bike route, downloading the route plus a 1-mile buffer either side for detours). A bounding box around a route like that would be enormous — most of the western US and half of Canada — so this has to clip along a *buffered line*, not a rectangle, to stay personalized and small. Critically, **this computation happens entirely on-device**, not on a server:
   - The route geometry comes from the user drawing it or importing a GPX file (from RideWithGPS, Komoot, Strava, etc.) — not from typing two city names and having the app generate the route. Auto-generating a cross-continent route would need an on-device routing engine plus a bundled global road/trail network graph — a real engineering lift, and a good candidate for a later phase, not part of the first version of this feature.
   - Given the route (drawn or imported), the device buffers it by the chosen distance (a cheap, well-understood geometry operation regardless of route length) and computes which tile coordinates intersect that buffer polygon (standard tile-grid math, also cheap).
   - The device then requests only those specific tiles. **The route itself never leaves the device** — only individual tile-by-coordinate requests do, which is the same low-sensitivity request the app already makes for ordinary browsing. This avoids what would otherwise be the single most revealing thing this app could send anywhere: an explicit record of someone's real, chosen trip, including possibly their home address as a start point.
   - One residual thing worth disclosing honestly rather than glossing over (same spirit as "the tile host problem" above): fetching hundreds of tiles in a tight burst, all falling along one coherent path, is a more distinguishable pattern in a tile host's server logs than someone panning around casually. No route is ever sent as data, but the shape can be inferred from request timing and geography. Not a blocker, just something the privacy policy shouldn't pretend away.

## Trailhead-based browsing (Phase 2 target — not yet built)

**The gap against today's build:** the Explore map currently renders every trail in a region as a bold orange overlay line, all at once, all the time. That's the Phase 1/2 proof-of-concept interaction, not the intended one — with hundreds of trails in a region (Big Bend alone has ~1,700 way segments), showing all of them at full visual weight overwhelms the screen and buries the trails someone's actually looking for.

**Target interaction:** trailheads — not individual trails — are what's visible by default.
- Individual trail lines are **not hidden**, but they render only as the basemap's own thin/dotted path styling (already part of `protomaps-themes-base`'s road network rendering, distinct from this app's bold orange trail-selection overlay) — present for context, not fighting for attention.
- Tapping a trailhead marker reveals the trail(s) that start there. One trail: it's selected immediately. Several: a picker list, and the map updates to highlight (bold) whichever one the user is currently looking at as they browse the list — "at a glance" preview before committing to a choice.
- Only the currently-selected trail gets the bold highlight treatment (reusing the existing `trails-line-selected` layer/pattern already built) — everything else stays at the dotted-basemap level regardless of how many other trails share that trailhead.

**Trailhead identification is a hybrid, decided deliberately:**
- Prefer real OSM `highway=trailhead` nodes where they exist.
- Fall back to algorithmically deriving a trailhead from trail-way endpoints (clustering nearby way start/end points) everywhere OSM's tagging doesn't have one — which today's regions overwhelmingly won't, since explicit trailhead tagging in OSM is sparse and inconsistent.
- This was chosen specifically so initial-build data gaps don't block the feature: it's fine — expected, even — for the automated pipeline to miss trailheads or mis-cluster a few at first. See "Community trail contributions" below for how gaps get fixed by the people who actually hike a given trail, rather than needing to be perfect on day one.

No new privacy surface here — trailhead markers are derived from the same public, already-bundled OSM trail data, just rendered and interacted with differently. Implementation is future work: no trailhead-derivation script, no picker UI, and no updated map-layer logic exist yet as of this writing.

## Community trail contributions (Phase 5 addition — not yet built)

The automated extraction pipeline (`src/data/scripts/`) will always miss trails and trailheads, and will always produce some data-quality artifacts an algorithm can't fully judge on its own — the clearest example found so far: a single named trail sometimes shows up as many small way segments (e.g. 0.1mi fragments) because of how OSM tagging or jurisdiction boundaries happened to split it, not because it's actually several separate trails. Nobody knows a trail better than the people who actually hike it, and this app can't get that right alone — so contribution is a real, planned feature, not an afterthought.

**Core decisions:**
- **Feeds back into real OpenStreetMap, not an app-only database.** A submitted trail becomes a real OSM way; a grouped set of fragments becomes a real OSM route relation. The whole OSM ecosystem benefits from a fix made here — every other OSM-based map and app, not just this one — and this app's data never drifts from what OSM shows elsewhere.
- **Requires the same lightweight pseudonymous account as reviews** (Phase 5's existing account system) — needed for attribution and moderation/abuse-prevention, even though browsing, favoriting, and everyday map use stay fully accountless. Contribution is opt-in on top of an already-opt-in feature set.
- **Two ways to submit a new trail: GPX import, or live GPS tracing.** GPX import needs no location permission at all — a user traces with a GPS device or app they already trust (Strava, Gaia GPS, a Garmin watch, etc.) and imports the resulting file. Live in-app GPS tracing is a further, **fully separate opt-in** — never required to contribute, foreground-only, no background location tracking (see the "Live GPS location" row in the data inventory above and the "Security & encryption baseline" section).
- **Fragment fix uses OSM route relations, not geometry editing.** The fragmented-trail problem gets solved by grouping existing way segments under one named route (`type=route, route=hiking`) — OSM's own idiomatic mechanism for exactly this situation, and one that never moves or reshapes a single existing point. This was chosen specifically over literal way-merging because it carries none of the conflict-resolution/versioning risk that editing someone else's existing geometry would — a route relation is purely additive organizational metadata.
- **Raw geometry editing (moving/reshaping an existing way someone else drew) is explicitly out of scope for this phase.** It needs real conflict-resolution and versioning machinery that new-trail submission and route-relation grouping don't, and is deferred to a later increment rather than bundled in now.

**Privacy note that must not get glossed over:** once a trail is submitted, it becomes public and permanent on OpenStreetMap under OSM's license (ODbL) — this is categorically different from every other on-device data type in this app (favorites, downloaded regions), which never leave the device unless the user takes a very deliberate action, and even then aren't published anywhere public. `docs/PRIVACY_POLICY.md` needs to disclose this plainly before the feature ships — deferred for now (see `docs/PROJECT_BRIEF.md`'s Current Status) since writing the policy language against a feature that doesn't exist yet risks drifting from what actually gets built.

## Traceability to core principles

Mapping each non-negotiable from [PROJECT_BRIEF.md](PROJECT_BRIEF.md) to how the architecture actually enforces it:

- *"No account required to browse/save/download"* → confirmed above: every Phase 0–4 row works with zero account system existing.
- *"Local-first storage"* → favorites and offline data rows are on-device only, no sync path exists to build a habit of assuming cloud storage.
- *"Community features opt-out by default"* → account/reviews rows default to Off, and there's no code path that turns them on without the user acting.
- *"No data collection or sale"* → analytics/ad ID row is a hard "not collected," not a toggle — there's nothing to sell because there's nothing collected.
- *"No third-party OAuth by default"* → addressed in open decisions below; default auth path is first-party.
- *"Security by design, always encrypted"* → "Security & encryption baseline" above: TLS 1.2+/1.3 only for every network request, encryption at rest scoped to personal/sensitive data, FIPS/STIG-grade practices as a design bar rather than a certification commitment.

## Open decisions (need your call before Phase 5)

6. **Auth mechanism for Phase 5.** Proposal: first-party email+password or passwordless email link as the default (no third party involved), with "Sign in with Apple" offered as an *optional* extra (not default) since Apple can relay a hidden email — still opt-in, still not Google/Facebook, consistent with the brief's rejection of third-party OAuth as a *default*. Needs your explicit sign-off since it's a real fork in direction.
7. **Backup retention window for deleted content.** Proposed 30 days for deleted reviews to fully purge from rolling backups. Arbitrary number, open to change.
8. **Any aggregate/opt-in telemetry, ever?** Current answer is a hard no — if a future feature wants "trail popularity," it should derive from public review counts (already-public data) rather than adding view tracking. Flagging so it's a deliberate choice if it ever comes up again, not a default we drift into.
9. **Route-corridor downloads: how regions are pre-sliced, and when (if ever) to build on-device route generation.** Confirmed direction: route geometry comes from drawing or GPX import, buffering/tile-selection happens on-device, nothing about the route is ever transmitted. Still open: how the world gets pre-sliced into named regions for selection mode 1 (political boundaries, like OrganicMaps? population-based? park boundaries?), and whether "type two cities, app generates the route" is ever built — it would need a bundled global routing network and an on-device routing engine, a big enough lift that it shouldn't be assumed as a v1 feature just because the buffer/tile-selection half is easy.
10. **OSM edit-submission mechanism for community contribution.** Not yet decided how a submission actually reaches OpenStreetMap — options include the standard OSM API directly (requires the contributing user to also have/link a real OSM account, since OSM attributes edits to its own accounts, not this app's), or a review queue where a project-level maintainer account applies vetted community submissions to OSM on contributors' behalf (adds a moderation step, but doesn't require every contributor to separately understand OSM's own account/editing system). Needs a real decision before Phase 5 contribution work starts.
